2.2 Protsess va Thread

Protsessor bir vaqtda faqat bitta instruksiya oqimini bajaradi, lekin mashinangizda yuzlab dastur «bir vaqtda» ishlaydi. Bu illuziyani OS ikkita abstraksiya bilan quradi: protsess va thread. Ular orasidagi farqni yuzaki bilish — server sig'imini noto'g'ri hisoblashning, tushunarsiz xatolarning va tuzatib bo'lmaydigan race condition'larning asosiy sababi. Bu darsda ikkalasini ichidan ko'ramiz.

Protsess: ishlab turgan dastur holati

Dastur — diskdagi passiv fayl (ELF binary): instruksiyalar va boshlang'ich ma'lumot. Protsess — o'sha dasturning ishlayotgan nusxasi, ya'ni 1.1-darsdagi ma'noda holat. Bitta /usr/bin/python3 faylidan 50 ta protsess ishlashi mumkin va ularning har biri butunlay mustaqil holatga ega bo'ladi.

Yadro har bir protsess uchun bitta katta tuzilma saqlaydi — Linux'da u task_struct:

Protsess holati nimalardan iborat (soddalashtirilgan)

struct task_struct {
    pid_t              pid, tgid;      // protsess va thread guruhi ID'si
    long               state;          // R / S / D / Z / T
    struct mm_struct  *mm;             // manzil fazosi: sahifa jadvali (2.3-dars)
    struct files_struct *files;        // ochiq file descriptor'lar jadvali
    struct signal_struct *signal;      // signal ishlovchilari
    struct cred       *cred;           // uid, gid, capabilities
    struct fs_struct  *fs;             // joriy katalog, ildiz katalogi
    struct sched_entity se;            // scheduler uchun hisob-kitob
    void              *stack;          // YADRO steki (har bir task uchun alohida)
    struct task_struct *parent;        // ota protsess
    struct nsproxy    *nsproxy;        // namespace'lar (konteynerlar shu yerda)
    ...
};

Demak protsess — bu «kod» emas, balki resurslar to'plami: manzil fazosi, ochiq FD'lar, huquqlar, joriy katalog, signal sozlamalari va bajarilish konteksti. Bu ro'yxatni yodda tuting — thread bilan farqni aynan shu ro'yxat belgilaydi.

Protsess holatlari: nega dastur ko'pincha «ishlamaydi»

Protsess doim ishlayotgan emas. Aslida tipik serverdagi protsesslarning katta qismi uxlab yotadi — 1.1-darsdagi «CPU vaqtning 10% idan kamini ishlaydi» xulosasi aynan shu holatlar orqali ro'yobga chiqadi.

Ko'p D holatidagi protsess = disk yoki tarmoq fayl tizimi javob bermayapti. Bu paytda yuklama o'rtachasi (load average) keskin oshadi, lekin CPU bo'sh turadi — chunki Linux'da load average faqat R emas, D holatidagi protsesslarni ham hisoblaydi. «Load 40, CPU 5%» degan holat aynan shundan kelib chiqadi va uni CPU muammosi deb tushunish klassik xato.

Protsess qanday tug'iladi: fork, exec, wait

Unix'da yangi protsess «yaratilmaydi» — u nusxalanadi. Bu g'alati ko'rinadi, lekin juda kuchli: fork() joriy protsessning deyarli to'liq nusxasini yaratadi, exec() esa o'sha nusxaning ichini yangi dastur bilan almashtiradi.

Klassik fork + exec + wait namunasi (shell aynan shunday ishlaydi)

#include <unistd.h>
#include <sys/wait.h>

pid_t pid = fork();          // shu yerdan keyin IKKI protsess davom etadi

if (pid < 0) {
    perror("fork");          // xato: xotira yoki protsess limiti
} else if (pid == 0) {
    /* FARZAND: fork() 0 qaytardi */
    execvp("/usr/bin/grep", (char *[]){"grep", "error", "log.txt", NULL});
    /* exec muvaffaqiyatli bo'lsa, bu qatorga umuman yetib kelinmaydi:
       protsessning butun kod va ma'lumot qismi almashtirildi */
    _exit(127);              // faqat exec xato bo'lsa bajariladi
} else {
    /* OTA: fork() farzandning PID'ini qaytardi */
    int status;
    waitpid(pid, &status, 0);        // farzand tugashini kutamiz
    if (WIFEXITED(status))
        printf("farzand %d kodi bilan tugadi\n", WEXITSTATUS(status));
}

Bu uch chaqiruv butun Unix protsess modelini tashkil qiladi:

  • fork() — manzil fazosi, FD jadvali va huquqlar nusxalanadi. Farzand 0 oladi, ota — farzand PID'ini.
  • exec() — joriy protsess ichidagi dasturni almashtiradi. PID o'zgarmaydi, ochiq FD'lar esa (odatda) saqlanadi — quvurlar shuning uchun ishlaydi.
  • wait() — farzand tugaganini kutadi va uning chiqish kodini oladi. Shu chaqiruvdan keyingina yadro farzand yozuvini butunlay o'chiradi.

Butun xotirani nusxalash sekin emasmi?

Yo'q — chunki hech narsa nusxalanmaydi. fork() copy-on-write (COW) ishlatadi: ota va farzand bir xil fizik sahifalarga ishora qiladi, sahifalar esa «faqat o'qish» deb belgilanadi. Kimdir yozmoqchi bo'lgandagina o'sha bitta sahifa nusxalanadi. Shuning uchun 4 GB xotira ishlatadigan protsessni fork() qilish millisekundlar oladi (mexanizmni 2.3-darsda ochamiz).

Yechim: docker run --init yoki tini kabi kichik init ishlatish.

Thread: bitta uyda bir nechta ishchi

Protsess qimmat: alohida manzil fazosi, alohida FD jadvali. Ammo ko'pincha bizga bir xil ma'lumot ustida ishlaydigan bir nechta bajarilish oqimi kerak bo'ladi. Shu yerda thread paydo bo'ladi: u protsess bilan deyarli hamma narsani bo'lishadi, faqat bajarilish uchun zarur minimumga alohida egalik qiladi.

Linux'da thread degan alohida narsa yo'q

Bu muhim tafsilot: Linux yadrosi uchun thread ham, protsess ham bir xil — task_struct. Farq faqat nima bo'lishilganida. Ikkalasi ham clone() chaqiruvi bilan yaratiladi, faqat bayroqlar boshqacha:

fork() va pthread_create() — bitta syscall, boshqa bayroqlar

// fork() aslida shunga yaqin:
clone(SIGCHLD, ...);                  // hech narsa bo'lishilmaydi → yangi protsess

// pthread_create() aslida shunga yaqin:
clone(CLONE_VM       |   // manzil fazosi UMUMIY
      CLONE_FS       |   // joriy katalog umumiy
      CLONE_FILES    |   // FD jadvali umumiy
      CLONE_SIGHAND  |   // signal ishlovchilari umumiy
      CLONE_THREAD,  ...);  // bitta thread guruhiga tegishli

// Natijada:
//   ps       → bitta protsess ko'rsatadi (tgid bo'yicha guruhlanadi)
//   ps -eLf  → barcha thread'larni alohida ko'rsatadi (TID bo'yicha)
//   /proc/PID/task/  → har bir thread uchun alohida katalog

Shuning uchun Linux'da «thread arzon» degani — «u kamroq narsa nusxalaydi» degani. Konteyner ham shu mexanizmning davomi: CLONE_NEWPID, CLONE_NEWNET kabi bayroqlar bilan ko'proq narsa ajratiladi.

Scheduler: kim, qachon va qancha ishlaydi

Tayyor (R) holatdagi task'lar yadrolardan ko'p bo'lganda kimdir tanlashi kerak. Buni scheduler qiladi va uning ikkita maqsadi bir-biriga zid: adolat (hamma ish oladi) va samaradorlik (kamroq almashinuv, ko'proq foydali ish).

Preemptiv ko'p vazifalilik

Zamonaviy OS majburiy almashtiradi: taymer uzilishi (odatda har 1–4 ms) yadroga boshqaruvni beradi va scheduler qaror qiladi — shu task davom etsinmi yoki boshqasi. Shuning uchun cheksiz sikl yozgan dastur mashinani qotirib qo'ymaydi.

Task qachon protsessorni tark etadi

  • Ixtiyoriy: bloklovchi syscall chaqirdi (read, sleep, qulf kutish) — S holatiga o'tadi.
  • Majburiy: vaqt ulushi tugadi (preemption) yoki yuqori prioritetli task uyg'ondi.
  • Tugadi: exit().

Adolat qanday o'lchanadi

Linux uzoq vaqt CFS (Completely Fair Scheduler) ishlatdi, 6.6 versiyadan EEVDF ga o'tildi. Ikkalasining g'oyasi bir xil: har bir task qancha protsessor vaqti «olishi kerak» edi va qanchasini haqiqatan oldi — shu qarzdorlik hisoblanadi va eng «kam olgan» task tanlanadi. nice qiymati shu hisobga og'irlik beradi: 

$ nice -n 10 ./hisobot.sh     # past prioritet: boshqalarga xalaqit bermasin
$ renice -n -5 -p 4210        # yuqori prioritet (root kerak)

# CPU'ni qat'iy cheklash (konteynerlarda shu ishlatiladi):
$ systemd-run --scope -p CPUQuota=50% ./worker    # cgroups orqali

# Qaysi yadroda ishlashini bog'lash (cache lokalligi uchun — 1.1-dars)
$ taskset -c 2,3 ./low_latency_app

CPU-bound va I/O-bound: ikki xil fuqaro

Scheduler uchun ikkita tur muhim. I/O-bound task ozgina ishlaydi va darhol uxlaydi (veb-server, DB mijozi) — u tez-tez uyg'onadi va unga tez javob berish kerak. CPU-bound task uzoq ishlaydi (video kodlash, hisoblash) — unga uzunroq ulush berish samaraliroq, chunki har bir almashinuv cache'ni buzadi. Shuning uchun ularni bitta mashinada aralashtirmaslik — 1.3-darsdagi «rollarni ajratish» qoidasining sababi.

Kontekst almashinuvining haqiqiy narxi

To'g'ridan-to'g'ri narxi ~1–5 µs. Lekin asosiy zarar ko'rinmas: yangi task cache va TLB'ni o'zinikiga almashtiradi, eski task qaytganda ularni qaytadan isitishi kerak. Shuning uchun 10 000 ta thread yaratish ishni tezlashtirmaydi — mashina foydali ish o'rniga almashtirish bilan band bo'ladi. vmstat 1 dagi cs ustuni shu almashinuvlar sonini ko'rsatadi.

Umumiy xotira — kuch va xavf

Thread'lar heap'ni bo'lishgani uchun ma'lumot almashish tekin. Xuddi shu sabab bilan ular bir-birining ma'lumotini buzishi ham tekin. Klassik misol:

Bir qatorlik kod — uchta amal

counter++;      // yuqori darajada bitta amal ko'rinadi, aslida uchta:
                //   1) LOAD  counter -> registr
                //   2) ADD   registr, 1
                //   3) STORE registr -> counter

// Ikki thread aralashib ketsa:
// T1: LOAD (5)              T2: LOAD (5)
// T1: ADD  -> 6             T2: ADD  -> 6
// T1: STORE 6               T2: STORE 6      → natija 6, 7 bo'lishi kerak edi

// Yechim 1: qulf
pthread_mutex_lock(&m);  counter++;  pthread_mutex_unlock(&m);

// Yechim 2: atomik amal (qulfsiz, tezroq)
__atomic_fetch_add(&counter, 1, __ATOMIC_RELAXED);

Bu xatoning yomon tomoni — u doim ko'rinmaydi. Sinovda 1000 martadan 999 tasi to'g'ri ishlaydi, ishlab chiqarishda esa yuklama ostida buziladi. Shuning uchun konkurent kodni «sinab ko'rib ishonch hosil qilish» ishlamaydi — uni to'g'ri loyihalash kerak.

Qulflar bilan bog'liq uchta muammo

  • Deadlock: T1 A qulfini ushlab B ni kutadi, T2 esa B ni ushlab A ni kutadi. Oldini olish: qulflarni har doim bir xil tartibda olish.
  • Raqobat (contention): hamma bitta qulfni kutsa, 32 yadroli mashina bitta yadroga aylanadi — bu 1.2-darsdagi ρ → 1 holatining o'zi.
  • Ushlab uxlash: qulf ichida read() yoki tarmoq chaqiruvi qilish. Qulfni ushlab turgan task uxlasa, uni kutayotganlarning hammasi to'xtaydi.
Amaliy qoida

Qulf ichidagi kod imkon qadar qisqa va bloklanmaydigan bo'lsin. Eng yaxshi qulf — umuman kerak bo'lmagani: ma'lumotni thread'lar orasida bo'lishish o'rniga, har biriga o'z nusxasini bering yoki xabar orqali uzating (Go kanallari, Erlang aktyorlari shu g'oyada).

Konkurentlik modellari: qaysi birini tanlash

1.2-darsdagi Little qonunini eslang: L = λ × W. Bir vaqtda 2000 ta so'rovni xizmat qilish kerak bo'lsa, «bir vaqtda» ni nima bilan ta'minlash masalasi turadi. Uchta asosiy javob bor:

ModelQanday ishlaydiKuchli tomoniChekloviMisol
Protsess-per-so'rov har bir so'rovga alohida protsess to'liq izolyatsiya, xato tarqalmaydi eng qimmat; minglab so'rov uchun yaramaydi eski CGI, PostgreSQL ulanishlari
Thread-per-so'rov har bir so'rovga thread; bloklovchi I/O kod oddiy va ketma-ket o'qiladi har bir thread stek va almashinuv talab qiladi; ~10k dan keyin qiyin klassik Java/Tomcat, Gunicorn
Event loop bitta thread epoll bilan minglab soketni kuzatadi juda arzon: xotira ham, almashinuv ham kam bitta bloklovchi amal butun loop'ni to'xtatadi nginx, Node.js, Redis
Yengil oqimlar (M:N) runtime ko'plab «goroutine» ni bir nechta OS thread'iga joylaydi oddiy ketma-ket kod + event loop tejamkorligi runtime murakkab; FFI va bloklovchi kod ehtiyot talab qiladi Go, Erlang, Java virtual threads

Diqqat: bu modellar bir-biridan «yaxshiroq» emas. Ular bir xil chegara bilan turlicha kurashadi — thread'ning narxi va bloklanishning narxi bilan. Qaysi birini tanlashingiz ishingiz CPU-bound yoki I/O-bound ekaniga bog'liq.

Thread pool hajmini hisoblash (1.2-darsdagi Little qonuni)

CPU-bound ish:   thread ≈ yadrolar soni        (ko'proq qilish faqat almashinuv qo'shadi)

I/O-bound ish:   thread ≈ λ × W
                 λ = 2000 RPS, W = 50 ms  →  100 thread + zaxira ≈ 130

Aralash ish:     thread ≈ yadro × (1 + kutish_vaqti / ish_vaqti)
                 8 yadro, 40 ms kutish, 10 ms ish  →  8 × 5 = 40 thread

# Va eng muhimi — pastdagi chegarani unutmang:
# 40 thread × 8 instance = 320 DB ulanishi. Postgres max_connections = 200 → avariya.

Amaliyot: protsess va thread'larni kuzatish

# Thread'lar bilan ko'rish
$ ps -eLf | awk '$6 > 1'        # NLWP ustuni — thread soni
$ top -H -p 4210                # thread darajasida CPU
$ ls /proc/4210/task/ | wc -l   # protsessdagi thread soni

# Protsess nima kutyapti (D holatida qotgan bo'lsa)
$ cat /proc/4210/stack          # yadro steki (root kerak)
$ cat /proc/4210/wchan          # qaysi yadro funksiyasida uxlayapti
$ cat /proc/4210/status | grep -E 'State|Threads|voluntary'
# voluntary_ctxt_switches   — o'zi uxlagan (I/O kutgan)
# nonvoluntary_ctxt_switches — majburan to'xtatilgan (CPU yetishmayapti!)

# Tizim bo'ylab almashinuvlar va navbat
$ vmstat 1

# r = tayyor task'lar (yadrodan ko'p bo'lsa — CPU to'yingan)
# b = D holatidagilar (disk kutilyapti)

# Protsess daraxti — kim kimni tug'dirgan
$ pstree -p 1 | head
Bitta ko'rsatkich — bitta xulosa

nonvoluntary_ctxt_switches tez o'sayotgan bo'lsa, protsessingiz CPU uchun kurashyapti — thread'lar sonini kamaytirish yoki yadro qo'shish kerak. Aksincha, voluntary ko'p bo'lsa — protsess ko'p kutyapti, ya'ni muammo CPU'da emas, I/O yoki qulfda.

Tez-tez qilinadigan xatolar

  • Thread sonini «ko'proq — yaxshiroq» deb oshirish Har bir ortiqcha thread stek, almashinuv va cache ifloslanishi qo'shadi. Little qonuni bilan hisoblang, keyin o'lchab tasdiqlang; pool'ni chegaralang.
  • Load average'ni CPU yuklamasi deb tushunish Linux'da u D holatidagi (disk kutayotgan) protsesslarni ham sanaydi. Load bilan birga vmstat dagi r, b va wa ustunlariga qarang.
  • Farzand protsesslarga wait() qilmaslik Zombie'lar to'planadi, konteynerlarda esa SIGTERM ham noto'g'ri tarqaladi. SIGCHLD ni ishlang yoki konteynerda --init / tini ishlating.
  • Thread'li dasturda fork() qilish Farzandda faqat bitta thread qoladi, lekin qulflar boshqa thread ushlab qolgan holatda nusxalanadi — natija deadlock. fork() dan keyin darhol exec() qiling yoki posix_spawn() ishlating.
  • Race condition'ni testlar bilan «tekshirish» U yuklama ostida, boshqa mashinada, boshqa vaqtda paydo bo'ladi. Umumiy holatni kamaytiring; -fsanitize=thread, go test -race kabi vositalarni ishlating.
  • Qulf ichida bloklovchi chaqiruv qilish Qulfni ushlab uxlagan thread butun navbatni to'xtatadi. Qulf ostida faqat xotira bilan ishlang; I/O ni qulfdan tashqariga chiqaring.
  • Event loop ichida og'ir hisoblash bajarish Node.js yoki Redis'da bitta sekin amal barcha mijozlarni to'xtatadi. Og'ir ishni worker thread yoki alohida protsessga bering (1.3-darsdagi worker roli).

Xulosa

  • Protsess — resurslar to'plami (manzil fazosi, FD'lar, huquqlar); thread — shu to'plam ichidagi bajarilish oqimi.
  • Protsess holatlari (R/S/D/Z/T) muammoni tashxislashning eng tez yo'li; D ko'p bo'lsa — disk, load yuqori-yu CPU bo'sh bo'lsa — shu sabab.
  • fork() + exec() + wait() — Unix protsess modelining uchta ustuni; COW tufayli fork arzon.
  • Linux uchun thread ham task — farq faqat clone() bayroqlarida, ya'ni nima bo'lishilganida.
  • Scheduler adolat bilan samaradorlikni muvozanatlaydi; har bir almashinuv cache'ni sovutadi, shuning uchun ortiqcha thread zararli.
  • Umumiy xotira tekin aloqa beradi, lekin race condition va deadlock xavfini ham beradi — qulf qisqa va bloklanmaydigan bo'lsin.
  • Konkurentlik modeli (thread-per-request, event loop, M:N) — bir xil chegara bilan kurashishning turli usullari; tanlov ish turiga bog'liq.
